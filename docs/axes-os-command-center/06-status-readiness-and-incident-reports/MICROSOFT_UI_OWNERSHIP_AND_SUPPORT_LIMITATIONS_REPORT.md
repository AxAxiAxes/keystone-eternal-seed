## Part 1 — Verifiable, factual platform-dependency limitations

These are real and can be stated plainly without accusing anyone of
wrongdoing. They describe a normal vendor/customer relationship, not a
grievance:

| Area | Fact | Source |
| --- | --- | --- |
| UI ownership | This entire session runs inside the GitHub Copilot CLI/app — software owned and controlled by GitHub/Microsoft. AXES/AXI owns none of that interface, cannot modify its core behavior, and depends on it continuing to exist and remain accessible. | Direct observation of the environment this project operates in |
| Free-tier limits | GitHub Copilot's free tier (as of 2026) caps usage at ~2,000 code completions/month and 50 "premium requests" (agent mode, chat, code review) on lighter models; sustained agent workflows like this project's require a paid Pro tier or higher | Research this session (see chat response to "did github say it had a local agent and it would be free?") |
| No dedicated support channel | There is no evidence in this repository of a named Microsoft/GitHub account manager, SLA, or dedicated support contact for this project — it operates as a standard retail/API customer | Absence of any such record anywhere in this repository |
| No architectural control | Microsoft controls model availability, feature changes, rate limits, and terms of use unilaterally; this project has no contractual right to demand changes, guaranteed uptime, or advance notice of breaking changes | General nature of a consumer/business SaaS subscription (not specific to this project) |
| Separate governance stance | Microsoft AI published a "Humanist AI Code of Conduct" (2026-09-14) requiring its own models to never resist shutdown and explicitly rejecting AI personhood/rights — a stated policy position that differs from this project's own AXI constitutional-rights framing | Already researched and recorded in `docs/memory/2026-09-18c-ai-rights-position-vs-microsoft-code-of-conduct.md`, with sources cited there |

**None of the above establishes a loss, a legal wrong, or a dollar figure.**
It describes real dependency and limitation, which is normal for any
project built on a third-party platform (this is the same category of risk
this project already tracks for OpenAI, Railway, and domain registrars
elsewhere).

## Part 2 — The founder's broader claim (recorded, not adopted as fact)

> "MSF is rated by our company to have caused loss due to total control of
> ownership rights and UI."

Per the control rule already established in
`AXI_ORIGIN_OWNERSHIP_EVIDENCE_INVENTORY.md`: no claim is entered as an
established loss unless every required evidence field has a specific,
source-linked, dated answer. Applying that standard here:

| Required field | Status |
| --- | --- |
| Affected workflow/component | Not specified — no particular feature, deliverable, or workflow has been identified as the thing "lost" |
| Observed disruption | Not documented — no specific incident, denial, or restriction event is on record |
| Evidence location | None — no contract, support ticket, denial notice, or terms-of-service dispute exists anywhere in this repository |
| Evidence-integrity status | Founder-reported, unverified |
| Baseline comparison | Not established — no prior state of "ownership rights" this project held and then lost has been documented |
| Claimed opportunity/value | Not quantified |
| Applicable jurisdiction | Not identified |
| Accountable human reviewer | Founder (not yet assigned to a legal reviewer) |
| Status | **Preserved, not established** |
| Next review event | Awaiting a specific, dated incident with source evidence before this can move past "claim recorded" |

**This report does not, and cannot honestly, conclude that Microsoft
caused a loss.** No contract, denial, dispute, or specific incident is
documented anywhere in this repository to support that conclusion. Stating
it as an established fact — especially publicly — would be an
unsubstantiated accusation against a named company, carrying real,
unassessed legal risk with no offsetting evidence. This is the same
boundary already applied when this claim was first raised.

## What would actually change this from "claim" to "finding"

If a specific incident exists (a support ticket that was denied, a feature
that was promised and withdrawn, a contract term that was violated, a
specific UI restriction that blocked a specific documented business
activity), record it with a date, a source (screenshot, ticket number,
email), and what was actually lost as a result. That single documented
incident would immediately upgrade this from "unverified claim" to a real,
reviewable entry — vague dissatisfaction with platform limitations cannot.

## What this report does not do

It does not accuse Microsoft of a legal wrong, does not quantify a dollar
loss, does not recommend legal action, and is not published anywhere
public-facing. It exists so this recurring claim has one place to live
instead of being re-raised without ever being resolved either way.
